## Problem

- 토마토는 기상 이변 등으로 가격 변동성이 상대적으로 높은 농산물이다.
- KAMIS 등에서 양질의 공공 데이터가 제공되지만, 유통업자가 매입 시점·물량을 판단(1순위)하거나 농업인이 출하를 판단(2순위)할 때 바로 쓸 수 있는 서비스는 부족해 보인다. (계획서의 문제의식. 선행 사례조사로 확인 필요)

## Proposed outcome

토마토의 3일 후·7일 후 도매/소매 가격을 예측하고, 그 결과를 자연어로 설명해 유통업자의 매입 시점·물량 판단(1순위)과 농업인의 출하 판단(2순위)을 돕는 시스템.

1. **데이터 파이프라인**: 공공데이터 API 우선(KAMIS, 기상청 등). API로 못 얻는 정보(뉴스·시장 동향 등)만 크롤링(Python + Playwright). 도매·소매 가격, 거래량, 출하량, 주요 생산지역 기상, 뉴스·자료를 수집해 날짜·지역·단위 통일, 중복·결측 정리 후 DB 저장. 일 1회 자동 실행, 실패 시 재시도 및 오류 기록.
2. **수치 예측 (ML)**: 도매 모델과 소매 모델을 각각 별도로 구현. 출력은 3일/7일 후 전국 평균 가격과 예상 등락률. 모델은 단순 기준선(전일 가격, 최근 평균)과 후보 모델들을 **같은 조건에서 비교**해 선택한다.
3. **해석 (LLM)**: LLM은 가격을 직접 예측하지 않고, ML 예측 결과와 최근 뉴스를 받아 쉬운 문장으로 설명만 한다(예상가격, 현재가와 차이, 주요 변동 원인, 주의사항). RAG는 뉴스가 충분히 쌓였을 때의 선택 사항.
4. **서비스**: 웹 대시보드(현재 도·소매가, 3일/7일 후 예상가, 그래프, 자연어 설명) + CLI(수집·예측·조회).
5. **배포**: Docker로 구성.
6. **3자 비교**: 상용·공공 토마토 가격 예측 서비스(사례 조사로 선정), 내 예측, 실제 가격을 대조 비교해 보고서에 넣는다.
7. **현장 검증**: 현장 사용자 2~3명에게 테스트하고 인터뷰해 결과를 보고서에 넣는다.

**기대효과**: 매입 비용 절감, 가격 급변 대비.

**Done looks like**
- 수집이 실패하면 재시도하고 오류를 기록한다.
- 각 모델이 기준선 대비 개선되었는지 동일한 평가 기준으로 보고됨. 개선이 없으면 없다고 보고하며, 수치를 맞추려고 평가 방식을 바꾸지 않는다.
- `docker compose up`으로 DB·API·대시보드가 실행되고, 수집·예측은 컨테이너 안에서 CLI로 실행된다.

**MVP 우선순위**: 마감이 짧으므로 아래 순서로 진행한다. 범위 축소 시 지도교수/바르카와 상의.
1. "도매 3일 후" end-to-end: 수집 → 기준선 vs 후보 모델 → LLM 설명 → 대시보드 한 화면 + CLI → Docker
2. 2차 현장 테스트
3. 3자 비교. 비교 가능한 서비스가 없으면 그 사실과 이유를 보고한다.
4. 소매·7일 후
5. RAG

**Out of scope**: LLM의 직접 가격 예측, 토마토 외 작물, 모바일 앱(웹을 반응형으로 지원하므로 별도 앱은 만들지 않음), 자동 매매·주문(도매 경매가 오프라인으로 이뤄짐).

**모델 후보** (2026-10 기준 조사, 모두 같은 시간순 검증으로 비교하며 라이선스는 사용 전에 각 저장소에서 확인):
- 기준선: 전일 가격, 최근 평균 (필수. 후보가 이 기준선을 이겨야 의미가 있음)
- 트리 부스팅: XGBoost / LightGBM / CatBoost (지연값·이동평균 등 feature를 직접 만들어 사용)
- 표 형식 파운데이션 모델: TabPFN 계열 (소규모 표 데이터에서 튜닝된 트리 모델을 앞선다는 벤치마크가 있음. 단 이 벤치마크는 시간 순서 데이터가 아니라 일반 표 데이터 기준이므로 이 프로젝트에서 그대로 성립하는지는 직접 검증 필요)
- 시계열 파운데이션 모델: Chronos-2 등 (학습 없이 예측 가능, 기상 같은 공변량 지원. GPU 활용 후보)

## Affected users and systems

- 사용자: 1순위 유통업자(중도매인, 소매·식당 바이어), 2순위 농업인 / 평가자: 지도교수, 바르카 / 유지보수: 개발자 본인.
- 외부: KAMIS, 기상청 API, 뉴스·시장 자료 사이트, LLM API.
- 내부: 수집기, DB, 예측 모델, LLM 해석 모듈, 웹 API/대시보드, CLI, Docker.
- 개발 환경: **Colab A100 GPU 사용 가능.**

### 가치 가설 (v3.1)

- 유통업자의 **매입 시점·물량 판단**을 지원한다: 3·7일 후 가격 방향, 급변 위험, 그 이유 설명.
- 대상·가치·예측 기간이 맞는지는 **가락시장 조사로 검증**하고, 틀리면 v4로 고친다.

### 사용자가 내리는 결정 (본인 답변)

- 유통업자·농업인이 예측 결과를 보고 **매입(출하) 시점과 물량을 정하는 것**을 지원 대상으로 본다.
- 도매가 자체는 경매 등으로 정해지는 것으로 보이며, 이는 현장 조사로 확인한다.
- 대부분은 기존 방식대로 결정하는 관성이 있겠지만, 데이터 기반 모델 결과나 보고서를 보고 결정하는 새로운 방식을 시도해 볼 소수가 있을 것이라고 본다.
- 이들에게 직접 접근해 판매(outbound sales)하는 것은 별개의 어려운 문제다.
- 현장에서 원래 어떻게 매입·출하를 결정하는지 조사해야 한다.
- 오늘 출하할지 미룰지 타이밍 판단을 돕는 방향은 괜찮아 보이지만, 현장에서는 다를 수 있다.
- 본인은 이 주제의 도메인 지식이 없는 상태에서 시작하며, 어디서부터 손댈지 정해야 하는 상황이다.

### 도매가와 소매가의 관점 (본인 답변)

- 도매가는 중간 유통업체·농업인의 관점, 소매가는 시장·마트에서 장보는 소비자의 관점이다.
- 각자 자신의 이익·효용이 목적이므로 두 관점은 구분된다.

### 바르카 (본인 답변)

- 위성사진으로 농산물 생산량을 예측하는 스타트업. 벤치마크에서 미국의 한 상업 예측 회사를 앞섰다는 기사를 본 적이 있다.
- **확인된 사실**: 바르카의 생산량 예측 API 등은 사용할 수 없다. 협업 프로젝트가 아니라 현업에 가까운 평가 기관 역할이다.
- 바르카가 무엇을 보고 싶어 하는지는 모른다.
- 본인 판단: 예측이라는 어려운 기술을 다루는 회사인 만큼, 작더라도 실제 국내 시장 사람들에게 테스트하고 보고서·인터뷰까지 결과물에 넣으면 인상적일 것이다. 기술로만 승부하는 방식은 아니지만 이런 접근도 의미가 있다고 본다.

## Constraints

- LLM은 가격을 예측하지 않고 설명만 한다.
- 도매와 소매는 별도 모델. 예측 대상은 3일/7일 후 전국 평균 가격 + 등락률.
- 평가는 (a) 실제와 예측 가격의 차이, (b) 상승·하락 방향 적중 정도 (구체 지표 `[미정]`).
- 데이터는 공공데이터 API 우선, 크롤링은 API로 얻을 수 없는 정보와 과거 데이터 확보가 불가능할 때 보조 수단.
- **일정**: 마감까지 약 20일(2026-11-17경), 실작업 약 2주. 일자별 상세 계획은 만들지 않고 단계별 완료 기준으로 진행.
- 1인 개발.
- Colab A100: 세션이 휘발성이고 Claude Code 실행 환경과 분리됨. 학습 결과(모델 파일, 지표)는 파일로 repo에 가져와야 함. GPU는 필수가 아니며 TabPFN/Chronos-2 등 GPU가 유리한 후보를 시험할 때 사용.
- 시간 순서를 지키는 검증(시간 기준 분할 / walk-forward). 예측 시점에 알 수 없는 정보를 feature로 쓰지 않는다.
- 크롤링 대상 사이트의 이용약관·robots 정책 확인.
- LLM 설명은 입력으로 준 예측값·데이터·뉴스에 근거해야 하며 근거 없는 수치·원인을 만들지 않는다.
- API 키·DB 비밀번호 등은 repo에 커밋하지 않는다(`.env`). 학번·주민등록번호 등 개인정보 문서(계획서 원본, 동의서)도 repo에 넣지 않는다.
- 현장 인터뷰는 참여 동의를 받고, 녹음은 별도로 동의를 받으며, 보고서에는 익명으로 쓴다.

## Open questions and my answers

1. **평가 지표** (MAE/MAPE/RMSE, 방향 적중률 정의, 성능 기준) — 아직 모르겠음. → Design에서 Claude와 함께 후보를 보고 결정.
2. **출하량·거래량 일 단위 출처** — 조사 필요. → `docs/research/data-sources.md`에 정리.
3. **품목 범위(품종·등급·단위), 전국 평균, 주요 생산지역** — 한국 농업계에서 통상 쓰는 기준을 따르고 싶음. → 조사 후 구체화. 조사 결과는 `docs/research/`에 기록.
4. **학습용 과거 데이터 확보** — 일 1회 수집은 앞으로의 데이터만 쌓으므로 2주 동안은 학습에 부족. **과거 기간을 일괄로 얻을 수 있는지가 최우선 조사 항목.** 크롤링은 하고 싶음(코드는 `src/collectors/` 안에 API 수집기와 함께 둠).
5. **LLM 제공자·비용 상한·뉴스 출처** — 미정.
6. **Docker 배포 대상, 스케줄링 위치** — 내 서버?(미정)
7. **사용자 평가 방법, 바르카 피드백** — 아직 공지 없음. 현장 사용자 2~3명 테스트·인터뷰를 산출물에 넣기로 함. 바르카는 평가 기관 역할이며 API 사용 불가(위 "바르카" 참고).
8. **일정** — 마감 약 20일 남음.
9. **선행 사례조사, 벤치마크 항목 1개 이상** — 진행 필요. → `docs/research/prior-work.md`, `benchmark.md`. 상용·공공 토마토 도매가 예측 서비스를 조사한 뒤, 그 서비스의 예측값·내 예측·실제 가격을 대조 비교해 보고서에 넣는다.
10. **jev** — 확인 결과 호스팅 전용 분류/점수화 모델. 이번 범위에서는 보류, 실험 후보로만 기록.
11. **모델 선정 근거** — 최신 모델(표 형식·시계열 파운데이션 모델 포함)을 포함해 같은 조건에서 비교하고 근거를 남긴다.
12. **최종 평가 방식**(데모·보고서·발표, 꼭 보여야 할 것) — 교수님께 확인 예정.
